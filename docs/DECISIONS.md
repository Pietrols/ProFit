## D9. Drizzle ORM instead of Prisma
D2 left the ORM to Phase 1 with Prisma 7 as the default. Prisma downloads an engine binary from
`binaries.prisma.sh` to run migrations, and that host is blocked in the cloud environment where
Claude Code builds ProFit, so migrations and database tests could not run there. Prisma 7 also
caused breaking-change friction in `legacy-v1`. Drizzle (`drizzle-orm` with the `pg` driver, and
`drizzle-kit` for migrations) is plain TypeScript with no binary or code generation step, and its
migrations are SQL files checked into `backend/drizzle/`. Tested end to end against Postgres 16
before choosing it. Changeable with a logged decision, but every table would need porting.

## D10. Google sign-in library
`react-native-nitro-google-signin` (MIT), which is one of the two libraries Expo's Google
authentication guide recommends. It uses Android Credential Manager, which Google now requires in
place of its deprecated sign-in SDK; the other recommended library only offers Credential Manager
in its paid version. Needs `react-native-nitro-modules` and a development build.

## D11. Sessions
The phone sends Google's ID token once. The API verifies it (signature against Google's public
keys, issuer, audience, expiry, verified email) with `jose`, then issues its own tokens: a JWT
access token valid for 15 minutes and an opaque refresh token valid for 60 days. Only a SHA-256
hash of each refresh token is stored. Refresh tokens rotate on every use, and presenting a used
one revokes the whole chain. The phone treats itself as signed in from what it has stored, so the
app opens offline.

## D12. Refresh retry window
A refresh token presented again within 60 seconds of its first use is treated as a retry and gets
a fresh pair, instead of being treated as stolen. On mobile data the server can rotate a token and
the reply can still be lost, and without this window those users would be signed out. Reuse after
60 seconds still revokes the whole sign-in. The phone also never runs two refreshes at once.

## D13. Developer sign-in
`POST /auth/dev` signs in any email so emulators, local testing and Claude Code sessions work
before Google OAuth clients exist. It is only mounted when `AUTH_DEV_LOGIN=true`, the config
refuses that setting in production, and the app only shows its button in development builds that
set `EXPO_PUBLIC_DEV_LOGIN=true`.

## D14. Profile fields
- Birth year instead of age, so it never goes stale. Accounts must be 13 or older.
- A unit system (metric or imperial, default metric) is stored now, because the launch is global
  and body weight logging in Phase 2 needs it.
- Body weight is not a profile field. It lives in the Phase 2 weight log.
- Display name comes from Google only at first sign-in; after that the user's own edit wins.

## D15. Mobile copies the API's types by hand
`mobile/src/features/profile/types.ts` mirrors `backend/src/me/dto.ts` and the enums in
`backend/src/db/schema.ts`. A shared package would need workspace tooling that caused trouble in
`legacy-v1`, and the contract is small. Rule: change both sides in the same commit. Revisit if the
shared surface grows enough that drift becomes a real risk.

## D16. Phase 1 storage on the phone
- Tokens and the signed-in user are kept together in the keystore (`expo-secure-store`, readable
  after the first unlock so the app can open after a restart).
- The cached profile and unsent profile edits are kept in `expo-sqlite`'s key-value store, filed
  under the user's id. Phase 2's local database and sync engine replace this.
- The web preview has no keystore, so it keeps both in the browser's localStorage. The preview is a
  development tool only.

## D17. Edits the server rejects as invalid are dropped
Unsent profile edits are retried until they reach the server. If the server answers 400 (the
values are invalid), retrying can never succeed and would block every later edit, so those fields
are dropped, the server's profile is kept, and You shows what was not saved. The profile form
checks the same limits as the API, so this should not happen in practice.

## D18. Signing out
- The app first tries to send unsent edits. Anything it cannot send stays on the phone, filed under
  the user, and is sent the next time that user signs in on this phone. The sign-in screen says so.
- Signing out offline cannot cancel the sign-in on the server; that refresh token simply expires
  after 60 days. The tokens are removed from the phone either way.
- When the server refuses a refresh token, the app signs out locally with a notice and keeps
  unsent edits the same way.

## D19. Onboarding endings
Four questions (name, goal, experience, where you train), each skippable. Finishing with at least
one answer marks onboarding completed; finishing with none marks it skipped; "Skip for now" marks it
skipped and keeps the answers given so far. A user whose profile has not reached the phone yet (for
example a reinstall opened offline) goes to the app, not back into onboarding.

## D20. Google button style
The sign-in button is ProFit's own pill with a monochrome Google mark, so it matches the theme and
works in the web preview. Google's branding guidelines ask for specific button styles; check the
button against them before release (Phase 11) and switch to the library's native button if needed.

## D21. Sync protocol
- Each record merges on its own: the copy with the later edit time (set by the phone) wins. Deletes
  are tombstones (`deleted_at`) so they sync like any other edit.
- One Postgres sequence numbers every write to every synced table, and pushes for one user take a
  per-user lock, so a phone can pull "everything after version N" without ever skipping a row.
- Edit times are capped at 5 minutes past the server's clock, so a phone whose clock runs ahead
  cannot win every future merge.
- Records the server rejects as invalid are listed in the reply and dropped on the phone with a
  visible message, the same rule as D17, so one bad record never blocks the rest.
- Pushes and pulls move at most 500 records per request; the phone loops until it is done.
- Rejected alternative: whole-document sync with a revision number. Simpler for one person's data,
  but every edit would resend everything, and community features need per-record rows anyway.

## D22. One weigh-in per day
A body-weight entry's id is a name-based UUID (version 5) from the user's id and the date, so two
phones that both log the same day produce the same id and merge into one entry instead of two.
The SHA-1 the UUID needs is written in plain TypeScript (`mobile/src/lib/uuid.ts`) and checked
against reference values, because the app has no crypto library yet. Random ids for other records
arrive with the first feature that needs them, using `expo-crypto`.

## D23. What stays outside the sync engine
- The profile keeps its own path (`PATCH /me` with the queue from Phase 1). It is one record edited
  field by field, which a field-level patch handles better than whole-record "later edit wins".
- The theme choice is a per-phone setting, saved in the key-value store. This completes D8.

## D24. Web preview and SQLite
The phone's database runs in the web preview through expo-sqlite's WebAssembly build, which needs a
cross-origin isolated page. Expo's dev server in SDK 57 sends the isolation headers on scripts but
not on the HTML page, and once a page is isolated, calls to the API on another port hang in the
browser. So the preview of signed-in screens is driven by a small browser harness that adds the
headers and reaches the API through the page's own origin. This only affects the development
preview; Android and iOS use native SQLite and talk to the API directly.

## D25. The exercise library ships with the app
Built-in exercises come from free-exercise-db (public domain, pinned commit, see Phase 3) and are
bundled as JSON instead of synced. They are the same for everyone, so syncing them would only cost
data; updates ship with app updates. Plans refer to built-ins by their slug, which stays stable
because the source commit is pinned. ProFit adds a few exercises the dataset lacks (burpee,
jumping jacks, wall sit, bird dog), written by us.

## D26. A "common" list drives search order and image order
About 90 exercises most people look for are marked common with a popularity rank. Search ranks
them above obscure variants with similar names, and images are made in that order, so the
exercises people see most get images first.

## D27. Photos are files, not database rows
A custom exercise photo is cropped square, shrunk to 1080 px and saved as JPEG on the phone, then
uploaded (`PUT /media/:id`) before the records that point at it, and fetched once by other
phones. The server keeps files on disk under `MEDIA_DIR` with a row per file; only the owner can
read them until sharing arrives in Phase 9. A photo the server refuses (too big, wrong type) is
not retried, and the user is told why. The web preview has no app folder, so photos are phone only.

## D28. New Expo modules for Phase 3
`expo-crypto` (random ids), `expo-image-picker` (gallery only: camera and microphone permissions
are off), `expo-image-manipulator` (crop and shrink), `expo-file-system` (keep, upload and

## D29. Exercise images are generated by Codex from a job list
Making 880 images by hand in a chat is not realistic, so each exercise gets a job (prompt, figure,
view, steps, file name) in `images/jobs.json`, and Codex, included with the ChatGPT plan, generates
them on a local copy of the repo, resuming from a log. Consistency comes from fixed rules

male by a hash of the exercise id, so the split is about even and never changes between runs.
The finishing step uses `sharp`, installed only in `scripts/` (its own package.json) for build
tools, never in the app.

## D30. Plan relationships and daily habit
Plan, day and exercise references are soft links so out-of-order sync accepts independently
edited records. Mobile scopes joins by user, hides children of deleted parents and tombstones
existing children when deleting a parent. A late child cannot resurrect a deleted parent.
The daily habit is an ordered exercise id list with one UUIDv5 id per user. Clearing the list
is a synced edit. No completion data is stored until Phases 5 and 6.

## D31. Difficulty and today's plan day
Gentle is 80% and Hard 120% of Standard reps, time and distance. Round to a whole rep,
second or metre, minimum 1, capped at the API limits. Sets and rest are unchanged.
Stored targets remain Standard so switching difficulty does not compound rounding.
A cycle advances after completion, not after a missed calendar day. A completion selects the next day immediately, including on the same calendar day.
Repeated reads of that completion keep selecting the same next day. Weekly days use the phone's local calendar date,
Monday 1 to Sunday 7. Missing weekdays mean rest. Phase 5 supplies completion records;
Phase 4 shows the first cycle day. If sync leaves several active plans, latest edit wins
with id as a stable tie breaker. These defaults can change with a logged decision.

## D32. Changing plan shape
Changing a cycle to weekly assigns existing days Monday onward in their current order; the
editor then lets the user choose different weekdays. More than seven days blocks the change
without losing data. Changing weekly to cycle clears weekday assignments. Targets, names and
exercise rows are preserved. Rest days keep existing targets so changing back loses nothing.

## D33. Workout snapshots and calculations (Phase 5 design)
Sessions preserve a bounded snapshot of the day at start, including Standard targets and chosen
log fields. Plan edits do not rewrite history. Sets have deterministic ids per session exercise
position and set index; only selected, entered values are stored. Stored units are kg, seconds
and metres. Easier today uses Gentle scaling from Standard for future prefills only.
PRs compare the same exercise id: heaviest load, reps at the same stored load, longest time and
Epley estimated 1RM for 1 to 10 reps (one rep uses the actual load). Ties are not new PRs; the
first eligible value establishes a record. Volume is external kg times reps, without estimated
body weight. Abandoned sessions do not advance plans or contribute PRs. A confirmed partial
finish advances a cycle; a cycle rest day has an explicit completion with no sets. Timers are
local timestamp state, never synced; notifications are operating-system effects of that state.
These are design defaults for steps 5.2 onward, not implemented behaviour or dependency approval.

D33 implementation clarification: a nonempty notes-only set is a valid result because Phase 4
permits any chosen log field, including notes alone. Empty input and done=false alone are not
a logged result. A deleted set can be explicitly logged again using its original slot id; a
deleted session cannot be resumed.

## D34. Workout history ordering and incomplete sets
Step 5.3 calculations take the signed-in user's session and log reads. Prefill uses only
completed sessions ending by the supplied cutoff; a summary compares sessions completed by
the current session's start, then earlier sets within the current session. Compare timestamp
instants, with set id breaking equal logged times. The latest edit per set id wins before
filtering tombstones or done=false, so an older copy cannot restore a removed result.
A recorded zero reps produces no load PR, even when a weight was entered. Weight-only logs
can establish a load PR; reps at an explicitly recorded zero weight can establish a reps PR.
Missing weight remains unknown, with zero volume contribution. Targets and configured rest
override history, including zero rest; notes, effort and done are never prefilled. The
functions copy snapshot arrays and do not modify plan targets or stored logs. These defaults
implement D33 and can change with a logged decision.

## D35. Workout form units and local timer recovery
Workout forms display weight in kg/lb and distance in metres/miles using the profile units.
Unchanged numeric prefills preserve their original values exactly, avoiding conversion and
rounding drift in PR comparisons. Edited values convert to kg/metres before validation.
Timer transitions use the existing per-phone key-value store, namespaced by user and session;
only the phone that starts a timer resumes it. Invalid saved state requires an explicit reset.
These choices need no new dependency. Keep-awake and notification modules still await approval.

## D37. Rest notification ownership and recovery
The approved expo-notifications module schedules local date-triggered rest alerts. The OS's
persisted request list is the notification-id ledger: each ProFit rest request carries user,
session, generation and deadline tags. Reconciliation compares it with the existing local timer
and active session rather than keeping a second, potentially inconsistent id file. Only tagged
rest requests are cancelled. Operations serialize; account/session revisions invalidate late
scheduling results. Logging, pause, reset, timer replacement, finish and sign-out cancel alerts.

Permission is requested only from Enable rest alerts. Android creates its channel first. iOS
requires full authorization because provisional delivery is quiet. Android's exact-alarm
permission is declared in app config; the user may still need to enable Alarms and reminders
in phone settings. The SDK falls back to inexact scheduling without that access. OS settings,
silent mode and battery restrictions may suppress or delay alerts; the UI does not promise
exact delivery. No remote push registration or background JavaScript is required. Web previews
show that native alerts are unavailable.

If a set committed after a saved timer began, recovery discards that old timer. Failed refresh
after a committed workout write is reported separately, so it does not skip the saved set's
timer transition. Phone verification remains required before Phase 5 is complete.

## D40. Bounded workout reads and exact historical comparisons
Home reads active session summaries and at most one latest completion for its plan, never set
logs. Resume controls receive that same read. History uses 25-row keyset pages ordered by start
instant descending and id ascending. SQLite expression indexes preserve Date.parse millisecond
semantics, including offsets and fractional seconds; they do not rewrite dirty canonical rows.
The versioned SQL expression is frozen because shipped migration indexes depend on it.

Live display state belongs in clock/readout components. Session results and prefills depend on
data revisions, not wall-clock ticks. Focused reads publish only for their current account and
request version; sync completion refreshes once. These parts are implemented and tested.

The remaining exercise-history read will use a rebuildable local projection of valid completed
results, with numeric performance/completion instants and indexed exercise/metric columns.
Canonical sessions and sets remain authoritative and retain their ids, timestamps and sync
metadata. SQLite triggers transactionally mark changed sessions dirty after local or sync writes;
projection reads repair those invalidations before returning comparisons. The projection is not
a synced collection, and losing it must not lose a workout. Initial rebuilds and warm reads need
separate query/row-count evidence. Do not claim phone timings from the Node fixture.

Fetch exact latest values and metric bests for the requested exercises, cutoff and candidate
loads, rather than clipping to the latest N workouts. Historical bests must respect completion
cutoffs and loggedAt/id ordering, including equal instants. Return only the representatives
needed for current-session calculations. Keep legacy pure-function entry points as equivalence
oracles while introducing the bounded input path. This contract was approved before the cache
code. Its implementation and verification are recorded in PHASE_5_CORRECTIONS.md.

## D41. Set corrections, undo and rest ownership
Step 5.8.4 uses transactional commands over existing set rows. A correction preserves id,
session, exercise position, slot, chosen fields and loggedAt; only values and edit metadata
change. A revision fingerprint includes the full saved result and deletion state, so even a
different result with an equal timestamp is stale. Edit times are strictly later than the
previous edit (at least one millisecond), without changing D21's server clock cap or merge rule.

Delete returns an undo receipt containing the prior values and the exact deletion revision.
Undo restores that identity only while that deletion still matches. Conflicts show the current
result and the attempted values; replacing/restoring a newer version requires an explicit UI
action and another fresh revision check. Failed local writes retain drafts. A successful write
followed by failed refresh remains saved and blocks another mutation until a fresh read.
These checks prevent stale local commands; simultaneous offline phones still follow D21's
latest-edit merge policy. Do not claim a server-wide compare-and-swap protocol.

New automatic rest timers carry an optional local sourceSetId, never a synced field. Editing
does not restart a timer or repeat a PR celebration. Deleting a linked source clears that rest;
startup recovery also discards it if its source is no longer an eligible result. Manual/legacy
unlinked timers are kept by deletion, with an explicit clear action available. The complete
native recovery/cancellation matrix remains in 5.8.11 and the physical 5.7 gate.

## D42. Negotiate sync compatibility before structural workout records
Step 5.8.5 begins with a transport compatibility slice. The authenticated capabilities endpoint
advertises supported protocol numbers, the minimum protocol and explicit feature names. A new
client checks it on every sync run, before media upload, push or pull. A missing endpoint,
unsupported protocol or missing required feature stops the run without clearing dirty rows or
advancing the cursor. An offline capability request remains an ordinary offline result.

Protocol 2 adds an explicit protocol number to push envelopes and pull queries. It still accepts
legacy record shapes. Initially the server accepts protocols 1 and 2, minimum 1, and advertises no
structural-workout feature: existing clients can continue syncing while this preparation ships.
No new item, slot or result format is enabled by this transport change alone.

Before enabling structural writes, commit the exact additive record contract and fixtures,
implement both stores/readers and their cache invalidation, then raise the server minimum to 2
and advertise the structural feature in the same compatibility slice. Reject a below-minimum
request with HTTP 426 before processing any record or producing a pull page, never as per-record
rejections. New clients require that feature before writing its records to the server. This
prevents an old client from skipping unknown collections and advancing its shared cursor.

Deployment is server first, then the app. At cutover, old installed apps keep working locally but
must upgrade to resume sync. Upgrading preserves their pending legacy edits; do not delete local
storage, change canonical identities or reset sync cursors as a shortcut. An old server's missing
capability endpoint similarly blocks the new client's sync and keeps every pending edit. D17's
ordinary invalid-record rejection policy and D21's latest-edit merge policy are unchanged.

## D43. Stable items and deterministic slots
The exact additive contract is in `docs/phases/WORKOUT_STRUCTURE_CONTRACT.md`. A synced item is
one exercise occurrence, independently ordered and linked to the unchanged original routine.
Slots are immutable item/index pairs with deterministic ids, so a separate synced slot table is
unnecessary for this phase's exercise-order and set-count operations. Planned slot ids preserve
the legacy namespace; added/replacement slots use their random item id as namespace.

Extend set_logs with a strict legacy/stable variant rather than assigning fake display positions
to added exercises. Capture effective targets only on new performance; do not manufacture them
for history. The first stable variant is bilateral. Per-side wire semantics and their client
compatibility gate are finalized in 5.8.10. Commit schema fixtures before migrations, preserve
pending legacy rows/tombstones, and complete indexed read compatibility before enabling writes.

Storage preparation used SQLite migration 8 to permit a null original position and restore
indexes/invalidation triggers after copying legacy columns. PostgreSQL migration 0005 added
only the item table and nullable metadata columns. Migration 0006 drops exercise_position's
NOT NULL constraint before the union serializer is registered. The completed 5.8.5 cutover
advertises workout_structure_v1 with minimum protocol 2 and requires it on the client before
sync. Normal workout logging now writes stable performances through the owned item/slot store.
Exercise adaptation controls are implemented in 5.8.6. Deploy server first, then app; preserve local
rows, tombstones and cursors throughout the upgrade.

## D44. Resolve structural records before counting performed work
The effective read model first scopes records to an owned session, then resolves revisions by
the existing numeric edit-time/tombstone/tie rules. Legacy and stable results share one identity
space; resolve them together before choosing a decoder so an older variant cannot reappear.
The original snapshot supplies deterministic planned views without writing canonical rows.
Malformed stored overrides block the affected planned view rather than silently restoring its
old active state. Report unavailable record ids so the UI can show incomplete data and block
structural commands until it is refreshed or repaired.

Performed results remain attached to valid removed/skipped/tombstoned items and retain their
performance targets. A missing or invalid owned parent keeps a result unavailable until that
parent arrives. Replacement links must resolve within the same owned session, including cycle
checks. Future work selection excludes unavailable, skipped and removed items; totals for
performed work still include their valid actual results. Preserve the legacy pure entry points
as equivalence oracles and reuse their metric calculations for both variants. Storage readers
return owned canonical data and issues; they do not fabricate positional ids for added items.

## D45. Log a new performance against the reviewed item revision
New stable logging reads the owned active session, effective item and existing slot in one
transaction. Compare the reviewed item revision, difficulty and easier-today setting before
capturing targets. A reorder can require a refresh but cannot send a draft to another item.
Reject skipped, removed, tombstoned, unavailable or out-of-range work before any write.

A live saved slot, including an explicitly incomplete result, is corrected through the existing
edit flow. Logging does not silently replace it or move its original performance time. A deleted
slot can be explicitly performed again with the same deterministic id, a fresh performance time
and newly captured effective targets. That new edit must sort after the deletion even if the
phone clock moved backward. Prior undo receipts then fail the full revision check. A deleted
legacy slot may become stable only through this explicit new performance; ordinary corrections
keep its legacy variant and unknown historical targets. Saving commits before any rest timer or
alert starts. Structural controls and sync cutover remain disabled until 5.8.5 is complete.

## D46. Apply session adjustments against reviewed owned revisions
Step 5.8.6 commands read the owned active session and complete effective item/result view in
one transaction. Reject unavailable data, ended sessions, stale reviewed items and stale order
snapshots. State changes preserve every result; skipped and removed work can be restored with
its original identity. Reasons are optional text of at most 500 characters. A command makes
its edit time later than the affected stored revisions even after a clock rollback.

Reorder and Do later change independent display positions only. Reorder validates the reviewed
order before writing changed positions, including virtual planned items that need an override.
Selection is account/session-local view state; it never completes work or rewrites the plan.
Choose the first outstanding slot of a selected active item, then fall back to the normal queue
when that item has no pending work. Saved incomplete slots remain reviewable through correction.

Set counts stay within 1 to 100. A local reduction removes only future tail slots and refuses
any tail containing a live saved result, including incomplete work. Delete a saved result
explicitly before omitting its slot. Late synced results beyond a reduced count remain eligible
actuals under D43; receiving one does not silently expand targets. Added sets use the existing
stable item/index namespace and never reuse an identity from another exercise.

Add and Replace use a fresh device-generated item id and a reviewed exercise/target snapshot.
Replacement atomically removes only the source's remaining work and adds a linked new item;
no values, fields or performance times are transferred. New exercise defaults follow the
existing library tracking rules. Targets remain editable for this workout. All related item
writes and history invalidations commit together or roll back together. Plan rows and original
session snapshots are never part of an adjustment write.

## D47. Display-unit adjustments and durable set drafts
Step 5.8.7 steppers add decimal digits exactly in the displayed unit, converting only on save.
Reps step by one. Weight defaults to 2.5 kg or 5 lb, with a visible increment choice. Blank minus
stays blank, blank plus starts at one increment and subtraction stops at zero. Malformed input
and adjustments outside canonical logging limits report an error without changing the text.

Draft recovery uses the existing local key-value store, scoped to account, session, item and
slot. A draft pins its display units, exact canonical prefills and all entered text, including

## D53. Publish media bytes and metadata as one revision
The pre-device review reproduced temporary-file collisions for concurrent uploads. It also
identified that replacing one owner's file and then updating metadata in a separate operation
can pair an older MIME type with newer bytes. Reserving ownership fixes the cross-account
claim race but cannot make those separate resources atomic.

Use a nullable SHA-256 file revision on the existing backend media row. Write immutable bytes
under owner/id/revision first, then atomically publish their revision, MIME type and size in the
owned row. GET reads the revision it selected, even if another upload completes meanwhile.
Existing rows with no revision retain the original owner/id file path. No mobile wire change
or new dependency is required. Use Node's crypto functions and unique temporary names, and
keep file IO outside database transactions. A failed write leaves the previous published
revision readable; first uploads with no file remain 404 and can be retried by their owner.

Old immutable revisions may remain on disk. Do not delete them during upload because a reader
may still hold that revision. Retention/garbage collection belongs with the Phase 11 media
backup and account-deletion work, and must preserve the current published revision.
